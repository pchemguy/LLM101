# Dissertation Introduction Linting Framework

## LLM-ориентированная система статического анализа введений диссертаций

Ниже — следующий, более мощный инструмент: не просто prompt для общей оценки, а **framework в духе linting / static analysis**, то есть система, заставляющая LLM анализировать введение как **структурированный объект с зависимостями, контрактами, дефектами и диагностическими правилами**.

Идея здесь такая же, как в инженерной проверке спецификации, архитектуры или кода:

* сначала извлечь структуру;
* затем восстановить логическую модель исследования;
* затем проверить зависимости между элементами;
* затем найти дефекты;
* затем выдать диагностический отчет.

Это особенно полезно для вашей задачи, потому что обычный “критический отзыв” от LLM все равно часто остается слишком свободным.
А linting-framework принуждает модель работать в режиме **проверки контрактов**.

---

# 1. Что такое “linting” применительно к введению диссертации

В данном контексте **linting введения** — это проверка текста по набору формализованных правил:

* наличие обязательных элементов;
* корректность их формулировки;
* согласованность между элементами;
* отсутствие типовых дефектов;
* достаточность научно-методологической определенности.

То есть LLM должен работать не как “рецензент-эссеист”, а как:

* **структурный валидатор**,
* **логический аудитор**,
* **методологический дефектоскоп**.

---

# 2. Главный принцип framework

Введение рассматривается как **Research Specification Object**.

```text
ResearchIntroduction
{
    ProblemContext
    KnowledgeState
    ResearchGap
    Goal
    Tasks[]
    Object
    Subject
    Methodology
    Methods[]
    DataBase
    ScientificNovelty[]
    PropositionsForDefense[]
    TheoreticalSignificance
    PracticalSignificance
    Reliability
    Approbation
    Publications
    DissertationStructure
}
```

Задача LLM:

1. **извлечь** эти поля из текста;
2. **проверить**, какие поля отсутствуют;
3. **оценить**, насколько каждое поле содержательно и корректно;
4. **проверить зависимости** между полями;
5. **выдать defects report**.

---

# 3. Основные режимы анализа

Framework можно использовать в трех режимах.

## Режим A — Structural Lint

Проверка наличия и минимальной внятности структурных элементов.

Подходит для быстрой первичной диагностики.

## Режим B — Logical Lint

Проверка логических связей между разделами.

Это уже полноценный методологический аудит.

## Режим C — Critical Research Design Audit

Максимально жесткий режим.

Он проверяет не только структуру и связи, но и:

* реальную научную нагрузку формулировок;
* дефекты новизны;
* фиктивную методологию;
* псевдозадачи;
* декларативные, но неработающие элементы.

Для серьезной оценки диссертационного введения нужен именно **режим C**.

# 4. Архитектура linting-проверки

## Шаг 1. Structural extraction

LLM должен сначала извлечь все компоненты введения в нормализованную форму.

### Извлекаемые поля

| Поле                    | Что извлекается                       |
| ----------------------- | ------------------------------------- |
| ProblemContext          | формулировка проблемы и ее значимости |
| KnowledgeState          | состояние научной разработанности     |
| ResearchGap             | нерешенный вопрос / пробел            |
| Goal                    | цель исследования                     |
| Tasks                   | список задач                          |
| Object                  | объект исследования                   |
| Subject                 | предмет исследования                  |
| Methodology             | методологическая основа               |
| Methods                 | конкретные методы                     |
| DataBase                | информационно-эмпирическая база       |
| ScientificNovelty       | список пунктов новизны                |
| PropositionsForDefense  | положения на защиту                   |
| TheoreticalSignificance | теоретическая значимость              |
| PracticalSignificance   | практическая значимость               |
| Reliability             | степень достоверности                 |
| Approbation             | апробация                             |
| Publications            | публикации                            |
| DissertationStructure   | структура диссертации                 |

На этом шаге нельзя еще ничего “додумывать”.
Если элемент не выделяется из текста явно или достаточно ясно, он должен быть помечен как:

* **explicit**
* **implicit but clear**
* **vague / weakly inferable**
* **absent**

Это очень важно, потому что многие введения создают **иллюзию полноты**, но при извлечении оказывается, что половина разделов только номинально присутствует.

# 5. Контрактная модель разделов

Каждый раздел должен проверяться как **контракт**: что именно он обязан делать.

## 5.1. Актуальность

### Contract

Раздел должен:

* показать существование значимой научной, практической или отраслевой проблемы;
* объяснить, почему проблема заслуживает исследования;
* связать значимость проблемы с тематикой диссертации.

### Defects

* общие слова без конкретной проблемы;
* подмена исследовательской значимости декларацией “тема важна”;
* макроконтекст без перехода к исследовательской задаче;
* отраслевой обзор вместо обоснования проблемы.

---

## 5.2. Степень разработанности

### Contract

Раздел должен:

* показать, что автор знает исследовательскую традицию;
* обозначить основные подходы;
* подвести к выявлению пробела.

### Defects

* просто список фамилий;
* перечисление авторов без анализа их вклада;
* отсутствие группировки подходов;
* отсутствие вывода о том, что именно осталось нерешенным.

---

## 5.3. Исследовательский пробел

### Contract

Пробел должен:

* быть явно или очень четко сформулирован;
* логически вытекать из степени разработанности;
* указывать, чего именно недостает в существующих исследованиях.

### Defects

* пробел отсутствует;
* пробел подразумевается, но не сформулирован;
* пробел слишком общий;
* пробел не научный, а просто тематический;
* пробел не связан с целью.

---

## 5.4. Цель

### Contract

Цель должна:

* отвечать на выявленный пробел;
* описывать итоговый научный результат;
* быть достаточно конкретной.

### Defects

* цель слишком широкая;
* цель является темой, а не результатом;
* цель описывает процесс (“изучить”, “рассмотреть”) без результата;
* цель не вытекает из пробела.

---

## 5.5. Задачи

### Contract

Задачи должны:

* быть шагами достижения цели;
* вместе покрывать цель;
* иметь исследовательский, а не декоративный характер.

### Defects

* задачи не ведут к цели;
* задачи дублируют друг друга;
* задачи описывают главы механически;
* задачи носят учебно-реферативный характер;
* задачи не содержат исследовательского действия.

---

## 5.6. Объект и предмет

### Contract

* объект — более широкая система, процесс, явление;
* предмет — конкретный аспект объекта.

### Defects

* объект и предмет совпадают;
* предмет шире объекта;
* объект слишком узок и совпадает с предметом;
* предмет описан как тема, а не как аспект объекта.

---

## 5.7. Методология и методы

### Contract

Раздел должен:

* описывать концептуальную базу;
* перечислять методы;
* показывать пригодность методов для решения задач.

### Defects

* формальный список методов без связи с задачами;
* перечисление общих подходов вместо реальной методологии;
* отсутствие методов;
* методы не позволяют получить заявленную новизну.

---

## 5.8. Научная новизна

### Contract

Раздел должен:

* перечислять конкретные результаты;
* фиксировать, что именно нового сделано автором;
* быть соразмерным цели и задачам.

### Defects

* новизна декларативна;
* пункты новизны не являются результатами;
* новизна состоит из банальных наблюдений;
* новизна не коррелирует с задачами;
* новизна по сути представляет собой обзор, описание или рекомендации без научного вклада.

---

## 5.9. Положения, выносимые на защиту

### Contract

Раздел должен:

* формулировать выносимые положения как содержательные результаты;
* коррелировать с новизной и основными результатами.

### Defects

* отсутствует;
* повторяет новизну без переработки;
* положения расплывчаты;
* положения не похожи на реально защищаемые результаты.

---

## 5.10. Достоверность

### Contract

Раздел должен:

* объяснять, почему результатам можно доверять;
* указывать основания достоверности: база данных, методы, апробация, сопоставление, верификация.

### Defects

* раздел отсутствует;
* достоверность заявлена декларативно;
* перечислены общие слова без оснований;
* нет связи с реальной методикой исследования.

---

## 5.11. Апробация

### Contract

Раздел должен:

* показать, где результаты обсуждались, внедрялись или публиковались;
* подтверждать внешнюю проверку результатов.

### Defects

* только формальное перечисление конференций;
* нет связи между апробацией и результатами;
* отсутствие публикационной/внешней проверки при заявленной высокой новизне.

---

# 6. Типы lint-rules

Framework должен проверять не только разделы, но и типы правил.

## 6.1. Presence rules

Проверяют наличие обязательного элемента.

Примеры:

* есть ли цель;
* есть ли научная новизна;
* есть ли положения на защиту;
* есть ли достоверность.

## 6.2. Adequacy rules

Проверяют, выполняет ли элемент свою функцию.

Примеры:

* актуальность действительно обосновывает проблему, а не просто фон;
* цель — это научный результат, а не декларация темы;
* новизна состоит из результатов, а не из действий автора.

## 6.3. Dependency rules

Проверяют согласованность элементов.

Примеры:

* gap → goal
* goal → tasks
* object → subject
* tasks → methods
* goal → novelty
* novelty → propositions for defense
* novelty → significance
* methods/data → reliability

## 6.4. Strength rules

Проверяют силу исследовательских формулировок.

Примеры:

* пробел конкретен или общий;
* цель операциональна или риторична;
* новизна существенна или слабая;
* практическая значимость реальна или шаблонна.

## 6.5. Anti-genericity rules

Проверяют, не подменяется ли содержательность клишированным академическим языком.

Примеры:

* “в современных условиях особую актуальность приобретает...” без конкретизации;
* “существенный вклад внесли...” без анализа;
* “разработаны рекомендации...” без указания их сущности;
* “полученные результаты могут быть использованы...” без конкретного режима применения.

# 7. Набор нормативных lint-checks

Ниже — уже почти готовый формализованный набор проверок.

## Block A. Structural completeness

### ST1

Проверить наличие обязательных компонентов по ГОСТ Р 7.0.11.

### ST2

Проверить наличие расширенных компонентов:

* объект;
* предмет;
* информационная база;
* публикации;
* структура диссертации.

### ST3

Проверить, являются ли компоненты самостоятельными и читаемо выделимыми, а не растворенными в неопределенном тексте.

---

## Block B. Problem formulation

### PR1

Есть ли в тексте реальная исследовательская проблема, а не только тематическая область?

### PR2

Показана ли значимость проблемы, а не просто общая важность темы?

### PR3

Есть ли переход от макроконтекста к конкретной исследовательской проблеме?

---

## Block C. Literature and gap

### LG1

Представлено ли состояние разработанности проблемы, а не только список авторов?

### LG2

Выделены ли основные подходы, школы, линии исследования?

### LG3

Сформулирован ли явный исследовательский пробел?

### LG4

Является ли пробел именно научным, а не просто указанием на “тему, которую еще можно изучать”?

---

## Block D. Research design

### RD1

Следует ли цель из пробела?

### RD2

Является ли цель научным результатом?

### RD3

Покрывают ли задачи цель?

### RD4

Нет ли среди задач реферативных, декоративных или второстепенных пунктов?

### RD5

Корректно ли соотносятся объект и предмет?

---

## Block E. Methodology

### MT1

Есть ли методологическая основа, а не только набор общих слов?

### MT2

Есть ли конкретные методы?

### MT3

Соотносятся ли методы с задачами?

### MT4

Могут ли заявленные методы привести к заявленной новизне?

### MT5

Есть ли достаточная информационно-эмпирическая база?

---

## Block F. Scientific contribution

### NV1

Представлена ли новизна в виде конкретных результатов?

### NV2

Коррелирует ли новизна с целью?

### NV3

Коррелирует ли новизна с задачами?

### NV4

Не состоят ли пункты новизны из тривиальных, описательных или учебных результатов?

### NV5

Можно ли считать заявленную новизну научно значимой хотя бы на уровне диссертации?

---

## Block G. Defense propositions

### DF1

Есть ли положения, выносимые на защиту?

### DF2

Соответствуют ли они новизне?

### DF3

Являются ли они реально защищаемыми тезисами, а не общими утверждениями?

---

## Block H. Reliability and validation

### RL1

Есть ли раздел о достоверности результатов?

### RL2

Указаны ли реальные основания достоверности?

### RL3

Есть ли апробация?

### RL4

Соотносятся ли данные об апробации с масштабом заявленных результатов?

---

## Block I. Significance

### SG1

Показана ли теоретическая значимость как вклад в знание?

### SG2

Показана ли практическая значимость как конкретный режим применения?

### SG3

Не являются ли формулировки значимости шаблонными и необязательными?

---

## Block J. Formal support and metadata

### FM1

Есть ли публикации?

### FM2

Есть ли структура диссертации?

### FM3

Поддерживают ли эти элементы общую верифицируемость введения?

---

# 8. Система уровней дефектов

Для linting-framework особенно важно не просто найти дефект, а классифицировать его.

## Critical defect

Фундаментальный дефект, делающий введение методологически несостоятельным или глубоко неполным.

Примеры:

* отсутствует исследовательский пробел;
* отсутствует цель;
* отсутствует научная новизна;
* отсутствуют положения на защиту;
* отсутствует достоверность при наличии серьезных эмпирических претензий.

## Major defect

Серьезный дефект, нарушающий логику исследовательского дизайна.

Примеры:

* цель не вытекает из пробела;
* задачи не ведут к цели;
* предмет не является аспектом объекта;
* методы не позволяют решить задачи;
* новизна не соответствует цели.

## Moderate defect

Существенный, но не фатальный дефект.

Примеры:

* слабая литература;
* пробел сформулирован расплывчато;
* методология формальна;
* значимость шаблонна;
* новизна частично описательная.

## Minor defect

Недостаток низшей тяжести.

Примеры:

* стилистическая избыточность;
* повторы;
* неудачная композиция отдельных фрагментов;
* формально присутствующий, но плохо оформленный служебный раздел.

# 9. Диагностические эвристики для LLM

Ниже — правила, которые сильно повышают полезность анализа.

## 9.1. Ambiguity = defect

Любая неясность, двусмысленность, неопределенность, расплывчатость должна трактоваться как дефект.

Не нужно “достраивать” текст за автора.

## 9.2. Formulaic presence ≠ adequacy

Наличие стандартной фразы не означает выполнения критерия.

Например:

* “актуальность обусловлена...” еще не означает качественной актуальности;
* “целью исследования является...” еще не означает хорошей цели;
* “научная новизна заключается...” еще не означает наличия научной новизны.

## 9.3. Genericity = weakness

Чем более общий, шаблонный и безоперациональный язык, тем ниже оценка.

## 9.4. Implicit element receives reduced credit

Если элемент лишь подразумевается, он не должен получать полную оценку.

## 9.5. Enumeration without synthesis = defect

Список авторов, факторов, методов, направлений без аналитической обработки — это неадекватная проработка.

# 11. Recommended master prompt for linting mode

Ниже — уже готовая prompt-заготовка именно для **linting / static analysis mode**.

```text
You are acting as a methodological auditor performing static analysis
of a dissertation introduction.

Your task is to analyze the introduction as a structured research specification.

You must work in Russian.

Your stance must be strictly critical, diagnostic, and methodologically severe.

You must identify as many defects, ambiguities, inconsistencies,
weak formulations, missing links, and pseudo-components as possible.

Anything vague, generic, weakly formulated, or logically unclear
must be treated as a defect.

Do not praise the author.
Do not soften criticism.
Do not infer missing elements unless they are clearly present in the text.

Treat formulaic academic language as insufficient unless it actually performs
the required methodological function.

You must perform the analysis in the following order:
```

# 12. Почему этот framework сильнее обычного prompt

Обычный prompt просит “оценить” текст.
Этот framework заставляет модель:

* сначала извлечь структуру;
* затем проверить контракты разделов;
* затем проверить зависимости;
* затем классифицировать дефекты;
* затем выдать не отзыв, а **дефектную карту**.

Именно это делает его похожим на:

* линтер;
* статический анализатор;
* ревизионный аудитор.

Для вашей задачи это особенно хорошо, потому что цель не “понравиться автору”, а **максимально жестко проявить все точки уязвимости текста**.

---

# 13. Практически важное ограничение

Даже такой framework не превращает LLM в окончательный арбитр качества диссертации.

Он лучше всего работает как:

* **первичный жесткий аудитор**;
* **инструмент методологической отладки текста**;
* **система поиска дефектов перед человеческой экспертизой**;
* **средство сравнения версий введения до и после правки**.

То есть его правильная роль — не заменить эксперта, а сделать проверку:

* более системной,
* более полной,
* менее случайной,
* более полезной для переработки текста.

# 14. Наиболее полезное следующее усиление

Самый полезный следующий шаг — превратить все это в **полный нормативный пакет из трех документов**:

1. **LLM Evaluation Standard**
   формальный стандарт критериев и шкал

2. **LLM Audit Prompt**
   рабочий prompt для оценки

3. **Defect Taxonomy / Codebook**
   справочник типовых дефектов с кодами вида:

   * GAP-01
   * GOAL-03
   * TASK-04
   * NOV-07
   * METH-02
   * GOST-05

Это даст уже почти промышленный уровень использования:
LLM сможет не просто критиковать, а **проставлять коды дефектов**, что очень удобно для итеративной переработки текста.

Следующим сообщением я могу сделать именно это:
**полноценный defect taxonomy / codebook для введений диссертаций**, пригодный для LLM-аудита и для ручной методологической проверки.
